⬡ tapeworm meeting reference · grace engineering · CNC program management
storage naming schema
▸Server filename = customer-partnumber.cnc
▸Swiss lathes are monolithic — one program per part, no op number needed
▸Mills with multiple setups: customer-part-op10.cnc
▸Revision lives in the DB, never in the filename
▸Use folder hierarchy not hyphens if customer names contain hyphens
O-number injection
▸O-numbers are meaningless — system assigns per-machine
▸machine_program_assignments(machine_id, program_id, o_number) — assigned once, permanent
▸Citizens: one O-number per file, top line only — injection is a single line swap
▸Mills: O-number + any M98 P____ call sites must all be rewritten atomically
citizen file structure — confirmed from actual programs
channels
▸$1 main spindle, $2 subspindle, $0 barfeed params — single file
▸NOT separate files per channel
subroutine calls
▸M98 H1 / M98 H100 = internal N-label calls, stay inside the file
▸/M98 P8000 = machine-resident utility, never send, flag as known
$0 block
▸Barfeed axis params are machine-specific — decision: strip on ingest or validate on send
▸!L___ labels = channel sync points, not subprogram calls — ignore in parser
pushback — have answers ready
▸Subprogram rewriting — mills M98/G65 call sites must all update, not just the header
→ stored as dependency graph, full bundle rewrite at transfer time
▸Receive-back mapping — program returns from machine with injected O-number, not filename
→ transfer record stores the substitution map, reverse lookup is deterministic
▸Operation number source — typed = drift, Plex routing = authoritative
→ pull from Plex work order routing via existing MCP integration
